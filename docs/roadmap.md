# 分期实施计划

本文按可验收产物划分阶段，不给出未经验证的时间估算。当前项目已有设计与技术栈文档，所有实现阶段均未开始。

前四期完成首版闭环，第五期验证第二个数据源。后续能力根据真实需求单独立项，不因出现在本文中就自动获得范围或发布承诺。

## 1. 阶段总览

| 阶段 | 目标产物 | 用户可见能力 | 完成后的状态 |
| --- | --- | --- | --- |
| 第 0 期 | AI 工程骨架与质量门禁 | 无 | AI 可以在一致环境中安全修改代码 |
| 第 1 期 | HealthEvent 契约 | 无 | 数据形状、指标和边界样例可机器校验 |
| 第 2 期 | 本地 HealthEventStore | 无 HA 界面 | 事件可幂等写入、查询、修正、删除和恢复 |
| 第 3 期 | HA 实体接入 | 配置映射并保存健康事件 | 形成 HA 状态到本地事件库的纵向链路 |
| 第 4 期 | 主动导出与体脂秤验收 | NDJSON、Webhook、审计 | **首个可发布 MVP** |
| 第 5 期 | bmc-e6-ha 适配 | 第二种设备与日期级数据 | 证明架构不是体脂秤专用方案 |
| 后续候选 | HealthTracker、MCP、FHIR 等 | 按单独提案确定 | 不排期、不预先引入基础设施 |

每期都必须通过完整自动门禁和独立 AI Review。前一期未通过核心验收，不用后一期功能掩盖问题。

## 2. 第 0 期：AI 工程骨架

### 目标

让完全 AI 编码从第一期开始就具备固定环境、明确上下文和可重复验证，而不是先生成大量代码再补工程约束。

### 交付物

- `pyproject.toml`、`.python-version`、`uv.lock`；
- uv、Ruff、Pyright、pytest 和 HA Integration 测试依赖；
- 根目录 `AGENTS.md`，记录工作边界、统一命令、敏感数据禁区；
- OpenSpec 目录和首个变更模板，将已接受文档转化为可验收规格；
- GitHub Actions CI，以及 hassfest 校验；
- 测试目录和合成数据约定；
- HA custom integration 最小 manifest，但不实现业务功能。

### 验收

- 干净环境可以通过锁文件重建开发与测试环境；
- Ruff、Pyright、pytest、契约脚本入口和 hassfest 能由 CI 重复执行；
- Agent 能从仓库内找到架构、规格、命令和禁止事项；
- 测试、示例和 CI 不包含真实个人健康数据；
- 一次最小改动可以走完“OpenSpec → 实现 → 门禁 → 独立 Review”流程。

### 明确不做

不搭 Docker、独立服务、前端、发布流水线或多 Agent 平台。

## 3. 第 1 期：HealthEvent 契约

### 目标

先统一数据语言，再实现存储和 HA 接入，避免不同 Agent 各自发明字段。

### 交付物

- Pydantic `HealthEvent`、`ObservedAt`、`Source`、`Provenance`、`Quality` 等模型；
- 自动生成的 `health-event.v1.schema.json`，CI 检查生成结果无漂移；
- 首批实际需要的指标：`body.weight`、`body.fat_percentage`、`body.bmi`；
- 单位与确定性转换规则；
- 稳定事件 ID 和规范序列化；
- 合法、非法和边界 golden vectors；
- 日期级时间、跨组件互斥、未知字段、非有限数值等拒绝规则。

### 验收

- 体重事件可以从规范输入生成预期模型和 JSON；
- 体脂率/BMI 能表达 `derived.vendor` 与 `estimated`；
- 日期级输入不会被补成虚构时刻；
- NaN、Infinity、不支持单位、未知字段和非法时间区间被拒绝；
- 相同身份输入生成相同事件 ID，非身份字段变化不影响去重身份；
- Schema、Pydantic 模型和 golden vectors 一致。

### 明确不做

不预先定义所有健康指标；血压、BMC、化验和 OCR 指标在对应来源进入时增加。

## 4. 第 2 期：本地 HealthEventStore

### 目标

在不依赖 HA 实体的情况下，先证明健康事件能够可靠保存、查询和恢复。

### 交付物

- 标准库 `sqlite3` 数据访问层；
- 事件表、必要索引列和 `payload_json`；
- 单写者锁、executor 包装、事务和唯一约束；
- WAL、外键、busy timeout、`synchronous=FULL`；
- 按测量者、指标和时间范围查询；
- 幂等写入、修正链、当前有效版本查询；
- 用户删除及删除后的查询行为；
- `user_version` 迁移、SQLite Backup API 和恢复检查。

### 验收

- 同一事件重复写入只保留一条；
- 多步写入中途失败不会留下半条事件或错误修正关系；
- 修正不会覆盖旧事件，默认查询能返回正确有效版本；
- 删除后活动数据库查询及后续导出不能恢复事件内容；
- 每个历史迁移版本都能升级到当前版本；
- 备份恢复后通过完整性、外键和业务不变量检查；
- 数据库操作不会阻塞 HA 事件循环；
- 磁盘错误、锁冲突和事务失败不会被报告为成功。

### 人工审批点

首次确定删除语义、迁移规则和备份边界时需要人工确认。不得承诺 SQLite 能保证 SSD 物理擦除或远程副本删除。

### 明确不做

不创建投递表或自动任务，不引入 ORM、PostgreSQL、保留期清理和性能遥测。

## 5. 第 3 期：HA 实体接入

### 目标

打通第一条 HA 状态到 HealthEventStore 的链路。

### 交付物

- 单实例 Config Entry、Config Flow 和 Options Flow；
- 类型化 `ConfigEntry.runtime_data` 和正确卸载流程；
- 用户选择源实体、测量者、设备、指标、单位和时间来源；
- 选定实体的状态变化监听；
- 确定性实体映射、单位转换和质量问题标记；
- 少量接入状态 Sensor；
- 合成体脂秤 HA fixtures 和 Integration 测试。

### 验收

- 用户无需 YAML 即可完成一个体重实体映射；
- 合成体重状态变化只生成一个规范事件；
- `unknown`、`unavailable`、非法单位和不支持值不会写入健康事件；
- OpenHealthRouter 自己的实体不会被递归摄入；
- 重启不会自动回填整段 HA Recorder；
- 卸载后没有监听器、在途任务或数据库句柄泄漏；
- 数据保存失败不会更新为接入成功；
- 默认配置没有外部网络投递。

### 明确不做

不实现设备发现、BLE/小米云协议、自定义仪表盘和复杂历史导入。

## 6. 第 4 期：主动导出与首个 MVP

### 目标

完成“接入、保存、筛选、导出、审计”的首个用户闭环，并用真实体脂秤验证语义。

### 交付物

- 统一 Export Policy；
- 按目标、指标、时间范围、质量和数据层级过滤；
- HA 管理员认证的流式 NDJSON 下载；
- 用户确认后的 HTTPS Webhook；
- 共享 aiohttp session、HMAC-SHA256、时间戳和投递 ID；
- 投递与审计存储，以及对应数据库迁移；
- 失败状态和用户明确重试；
- 真实体脂秤的人工确认记录，以及脱敏后的回归向量；
- 安装、备份、恢复和隐私说明。

### 验收

- NDJSON 与 Webhook 对同一请求产生完全一致的事件集合；
- 导出最近 3 天体重不会包含其他指标、日期或默认排除的原始属性；
- 非管理员不能通过下载视图读取健康数据；
- Webhook 签名与发送 body 完全一致，超时和失败不会伪报成功；
- 外部服务不可用时本地事件仍保留，用户可明确重试；
- 日志、审计、诊断和 CI 产物不含健康值或密钥；
- 真实体脂秤的体重、体脂率、测量者和时间语义经用户确认；
- 全部门禁和独立 Review 通过后，才标记为首个可发布 MVP。

### 人工审批点

网络出口、密钥处理、下载权限、数据库迁移和首次发布必须明确审批。真实设备数据只在用户本地验证，不提交仓库。

## 7. 第 5 期：bmc-e6-ha 第二连接器

### 目标

用结构不同的数据源验证契约、去重和时间模型是否通用。

### 交付物

- bmc-e6-ha 适配器及其实际需要的指标契约；
- `recordNo` 原生 ID 映射；
- 日期级观察和治疗区间；
- BLE、云端、mini-agent 来源接收与去重；
- 设备观察和厂商派生评分的分离；
- 多来源接收记录（若现有单 `source` 模型不足，通过 OpenSpec 做兼容扩展）；
- BMC golden vectors 和端到端测试。

### 验收

- 同一设备同一 `recordNo` 的同一指标经不同通道到达时不重复计数；
- 不同设备的相同 `recordNo` 不会被错误合并；
- 只有日期时保持 `precision: day`；
- 云端评分带 `derived.vendor`，不会覆盖设备观察；
- bmc-e6-ha 主体采集逻辑无需重写；
- 历史 730 条热数据上限不会被当作统一健康库上限；
- 第 4 期体脂秤回归测试全部保持通过。

### 明确不做

不抽象通用 Connector SDK，不预先支持第三、第四种设备。第二个连接器完成后再判断哪些代码值得复用。

## 8. 后续候选，不固定顺序

| 候选能力 | 解锁条件 | 新增负担或边界 |
| --- | --- | --- |
| HealthTracker Bridge | 首版存储、去重和授权稳定，移动端确有同步需求 | 新增外部摄入 API、认证、重放保护和移动端离线队列 |
| 确定性统计与覆盖率 | 已有足够真实事件和明确查询需求 | 新增统计口径、数据覆盖和证据引用测试 |
| 只读 MCP / AI 查询 | 查询与授权边界已验证，用户主动选择 Provider | 新增外部数据暴露面；禁止直接读 DB 和自动医学判断 |
| FHIR / Open mHealth 导出 | 出现明确接收系统 | 新增映射、兼容性和外部标准测试 |
| 自动同步与 Outbox | 用户明确接受无人值守外发 | 新增长驻任务、重试、撤销、运维和隐私风险 |
| 独立 Add-on / REST API | 外部客户端无法通过 HA Integration 合理接入 | 新增进程、部署、认证、备份和升级成本 |
| PostgreSQL / TimescaleDB | 实测证明单进程 SQLite 不满足规模或多写者需求 | 新增数据库服务和恢复运维 |
| 自定义前端 | Config Flow 和 HA 原生视图无法承载关键工作流 | 新增 Lit/TypeScript 构建与发布链 |

每个候选都必须有独立 OpenSpec 提案，不能因为技术栈文档提过就默认实施。

## 9. 每期统一完成定义

每期结束时，主 Agent 必须提交以下证据：

1. OpenSpec 验收场景逐条对应到测试结果或明确的人工验证记录；
2. Ruff、Pyright、契约检查、pytest、hassfest 和 CI 全部通过；
3. 独立 Review 没有正确性、安全、迁移或隐私阻断项；
4. 数据库 Schema、JSON Schema、文档和代码版本一致；
5. 所有新测试使用合成数据，真实设备验证结果已脱敏；
6. 当期非目标没有被“顺便”实现；
7. 人完成当期要求的审批后，才允许合并或发布。

## 10. 任务拆分原则

- 一个 OpenSpec change 只解决一个可验收能力，不按“完成整个平台”派任务。
- 契约、存储、HA 接入和导出可以分派不同 Agent，但只有文件不重叠时才并行。
- 每个实现任务同时更新直接相关测试和调用方，不留下“以后再补”的破损状态。
- 评审发现的问题优先检查是否来自过度机制；能通过删除机制解决就不继续加固。
- 后续阶段需要推翻前期假设时，先修改规格和迁移设计，再修改代码。
