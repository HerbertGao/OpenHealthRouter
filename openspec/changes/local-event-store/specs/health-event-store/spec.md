# Spec Delta

## Purpose

健康事件本地持久化能力：把已校验的 HealthEvent 可靠地保存、查询、修正与删除，并在版本迁移和备份恢复后保持数据完整，是实体接入与导出共同的数据底座。

## ADDED Requirements

### Requirement: 幂等写入

存储 MUST 接受已通过契约校验的事件并以 `eventId` 为唯一键写入。同一 `eventId` 再次提交 MUST 立即按"已存在"返回，MUST NOT 产生第二行、MUST NOT 覆盖已保存内容，且该判定 MUST 先于任何其他写入副作用（取代标记更新、修正目标检查）。并发提交同一事件时，最终数据库中 MUST 恰好存在一行。

#### Scenario: 首次写入新建事件

- **WHEN** 存储收到一个此前不存在的 `eventId`
- **THEN** 该事件被保存，写入结果报告为新建

#### Scenario: 重复写入不产生第二行

- **WHEN** 同一 `eventId` 的事件被提交两次
- **THEN** 数据库中该 `eventId` 只有一行，第二次写入报告为已存在，且原有内容不变

#### Scenario: 修正目标已删除时重复提交仍报告已存在

- **WHEN** 事件 B 以 `correctionOf = A` 写入成功，随后 A 被删除，之后再次提交同一 B
- **THEN** 写入报告为已存在且不抛错，库中仍只有一行 B

#### Scenario: 并发提交同一事件只保留一行

- **WHEN** 多个写入请求并发提交同一 `eventId`
- **THEN** 写入完成后该 `eventId` 在数据库中恰好一行，且每个请求的返回均为"新建"或"已存在"，不出现未定义的第三种状态

### Requirement: 修正链与当前有效版本

事件内容 MUST NOT 被原地修改，唯一例外是用户删除事件时清除其修正引用。修正 MUST 以新事件表达，并通过 `correctionOf` 指向被修正事件；写入修正时 MUST 在同一事务内把被修正事件标记为已被取代，该标记 MUST NOT 因删除其他事件而清除。默认查询 MUST 只返回未被取代的事件，无论链有几级；按事件 ID 精确检索 MUST 仍能取回被取代的历史事件。

#### Scenario: 修正后默认查询只返回最新版本

- **WHEN** 事件 A 已保存，随后事件 B 以 `correctionOf = A` 写入
- **THEN** 默认查询只返回 B，不返回 A

#### Scenario: 多级链只返回最新版本

- **WHEN** A 被 B 修正，B 又被 C 修正
- **THEN** 默认查询只返回 C；A 与 B 均不出现

#### Scenario: 被修正事件仍可按 ID 取回

- **WHEN** 按 A 的 `eventId` 精确检索
- **THEN** 返回 A 的原始内容，且能看出它已被取代

#### Scenario: 删除链中事件后旧版本不复活

- **WHEN** A 被 B 修正、B 被 C 修正，随后删除 B
- **THEN** 默认查询仍只返回 C，A 仍保持已被取代状态，不重新计入当前集合

#### Scenario: 删除最新版本后该测量无当前值

- **WHEN** A 被 B 修正、B 被 C 修正，随后删除 C
- **THEN** 默认查询为空集，A 与 B 仍为已被取代状态；显式请求包含被取代事件时可取回 A 与 B

#### Scenario: 修正指向不存在的事件被拒绝

- **WHEN** 写入一条此前不存在的、`correctionOf` 指向库中不存在事件的记录
- **THEN** 写入被拒绝，库内容不变

#### Scenario: 批次内的修正引用必须后置

- **WHEN** 同一批次同时包含事件 A 与其修正事件 B，且 B 在 A 之前出现
- **THEN** 该批次被拒绝，库内容不变

### Requirement: 按测量者、指标与时间范围查询

查询 MUST 支持按测量者、顶层 `metric` 与时间范围过滤（组件级 `components[].metric` 过滤不在本期范围），MUST 支持分页与跨页稳定排序，MUST 返回与过滤条件一致的总数，单页返回条数 MUST NOT 超过给定上限。时间过滤 MUST 采用半开区间（左闭右开）的相交语义：瞬时事件 MUST 在 `q_lo <= 观察时间 < q_hi` 时命中；区间事件 MUST 在 `起点 < q_hi 且 终点 > q_lo` 时命中。日期级精度的观察 MUST 视为按事件时区解析的整天区间（自带 `end` 时视为覆盖 `start` 至 `end` 的整天区间）参与比较，并 MUST 在返回内容中保持日期级形式。

#### Scenario: 按指标与时间范围过滤

- **WHEN** 库中存在不同指标、不同观察时间的事件，查询指定顶层指标与时间范围
- **THEN** 只返回该指标且观察区间与查询区间相交的事件

#### Scenario: 日期级事件落入范围

- **WHEN** 某事件仅有日期级观察时间且该日期落在查询范围内
- **THEN** 该事件出现在结果中，且返回内容的日期与精度仍是日期级

#### Scenario: 日期级区间事件覆盖其声明的全部日期

- **WHEN** 某事件的观察时间为 `{start: "2026-11-12", end: "2026-11-13", precision: "day"}`，分别查询 11-12 与 11-13
- **THEN** 两次查询均命中该事件，且其区间上界等于 11-14 当地午夜对应的瞬时

#### Scenario: 日期级事件不落入相邻范围

- **WHEN** 查询范围是某单日日期级事件所在日期（以事件时区为基准）的前一天或后一天
- **THEN** 该日期级事件不出现在结果中

#### Scenario: UTC 日界对齐的查询与日期级事件部分相交

- **WHEN** 查询区间按 UTC 日界对齐，且与某日期级事件所在的当地日期部分相交
- **THEN** 该事件出现在结果中（区间相交语义下的正确行为）

#### Scenario: 瞬时事件恰在查询下界被包含

- **WHEN** 某瞬时事件的观察时间恰好等于查询区间起点
- **THEN** 该事件出现在结果中

#### Scenario: 瞬时事件恰在查询上界被排除

- **WHEN** 某瞬时事件的观察时间恰好等于查询区间终点（右开）
- **THEN** 该事件不出现在结果中

#### Scenario: 区间事件恰在查询下界结束被排除

- **WHEN** 某区间事件的观察终点恰好等于查询区间起点
- **THEN** 该事件不出现在结果中

#### Scenario: 起点在查询区间内、终点在区间之后的区间事件被包含

- **WHEN** 某事件观察区间从查询区间之内开始、在查询区间之后结束
- **THEN** 该事件出现在结果中

#### Scenario: 起点在查询区间之前、终点在区间之内的区间事件被包含

- **WHEN** 某事件观察区间从查询区间之前开始、在查询区间之内结束
- **THEN** 该事件出现在结果中

#### Scenario: 覆盖查询区间的区间事件被包含

- **WHEN** 某事件观察区间完全覆盖查询区间
- **THEN** 该事件出现在结果中

#### Scenario: 分页稳定不重不漏

- **WHEN** 同一查询分页读取全部结果，期间没有新的写入
- **THEN** 各页合并后与一次性读取的结果集合完全一致，且顺序稳定

#### Scenario: 总数与单页上限

- **WHEN** 匹配事件多于单页上限时以较小上限分页查询
- **THEN** 返回条数不超过上限，且总数等于不分页时匹配到的条目数

#### Scenario: 空结果不报错

- **WHEN** 查询条件不匹配任何事件
- **THEN** 返回空集合与零计数，不抛出错误

### Requirement: 用户删除

删除 MUST 按事件 ID 执行并 MUST 使该事件的内容在本地查询中不可再取得。删除 MUST NOT 静默扩大范围到用户未选择的其他事件：被删除事件作为修正目标的引用 MUST 在列与事件内容中同时被清除，指向它的其他事件内容 MUST 保留，且其他事件的已被取代标记 MUST NOT 被删除操作清除。删除不存在的事件 MUST 报告为未删除而不是报错。存储 MUST NOT 承诺物理介质擦除，也不得声称删除会作用于既有备份或已导出副本。

#### Scenario: 删除后内容不可查询

- **WHEN** 事件被删除后按 ID 或按范围查询
- **THEN** 查不到该事件的任何内容

#### Scenario: 删除被修正事件时保留其他事件

- **WHEN** 删除 A，而 B 通过 `correctionOf` 指向 A
- **THEN** A 的内容不可再取得，B 仍可查询，且按 ID 取回的 B 中不再包含指向 A 的修正引用

#### Scenario: 清除引用后载荷仍是规范事件

- **WHEN** 删除导致 B 的修正引用被清除
- **THEN** B 的存储载荷与按契约模型重新序列化得到的结果一致，且 `eventId` 与删除前相同

#### Scenario: 删除不存在的事件

- **WHEN** 删除一个库中不存在的 `eventId`
- **THEN** 结果报告为未删除，库内容不变，不抛出错误

#### Scenario: 批量删除只影响所选事件

- **WHEN** 一次删除请求包含多个 `eventId`，其中部分存在
- **THEN** 存在的事件全部被删除，未选中的事件保持不变，结果分别报告已删除与未删除数量

### Requirement: 事务原子性与失败可见

一次写入涉及的多步变更 MUST 在同一事务内提交，任一步失败 MUST 整体回滚，使库中不出现半条事件或指向不存在事件的修正引用。事务失败、磁盘错误或锁冲突 MUST 报告为失败，MUST NOT 返回成功。

#### Scenario: 中途失败不留半条数据

- **WHEN** 批次写入中某条违反约束导致事务未完成
- **THEN** 该批次的所有变更全部不可见，库内容与写入前一致

#### Scenario: 锁冲突不虚报成功

- **WHEN** 另一连接持有写锁超过本连接等待上限
- **THEN** 写入调用返回失败，库内容不变，且失败不被记为已保存

#### Scenario: 只读数据库写入失败

- **WHEN** 数据库文件不可写
- **THEN** 写入调用返回失败，而不是报告为已保存

### Requirement: 版本化迁移

数据库 MUST 通过 `PRAGMA user_version` 记录 schema 版本，并 MUST 按递增版本顺序执行迁移。每个迁移 MUST 在显式事务内完成，DDL 与版本号推进同属该事务；任一迁移失败时 MUST 回滚全部 DDL、保持原版本，并把存储置于拒绝写入状态。对已是当前版本的数据库再次初始化 MUST 不重复执行迁移。

#### Scenario: 新库初始化到当前版本

- **WHEN** 对一个空数据库初始化存储
- **THEN** 完成后版本号等于当前 schema 版本，且表与索引齐备

#### Scenario: 旧版本库升级后已有事件完整

- **WHEN** 打开一个处于历史版本且已有事件的数据库
- **THEN** 完成全部未应用迁移，已有事件在升级后按 ID 与按范围均可完整查询

#### Scenario: 重复初始化不重复迁移

- **WHEN** 对已处于当前版本的数据库再次初始化
- **THEN** 不执行迁移，版本不变，已有数据不变

#### Scenario: 迁移失败回滚且拒绝写入

- **WHEN** 某个迁移执行失败
- **THEN** 数据库版本保持迁移前的值，表与索引恢复为迁移前状态，存储拒绝后续写入并报告失败原因

#### Scenario: 修复后可再次迁移

- **WHEN** 迁移失败后修正迁移实现并重新打开同一数据库
- **THEN** 迁移成功完成，版本推进，存储恢复可用

### Requirement: 一致性备份与恢复校验

备份 MUST 通过数据库引擎提供的备份接口生成一致性快照，MUST NOT 以直接复制主数据库文件的方式充当运行中备份。恢复校验 MUST 执行完整性检查、外键检查、期望值解析（期望值随备份持久化）与真实读取并比对，任一失败（含数据库引擎抛出的错误）MUST 报告恢复不可用。

#### Scenario: 备份快照包含全部已提交事件

- **WHEN** 在存在未合并日志且未关闭连接的状态下生成备份，再用该备份打开存储
- **THEN** 事件数量与内容与备份时一致

#### Scenario: 恢复后检查不变量

- **WHEN** 从备份恢复数据库
- **THEN** 完整性检查与事实外键检查通过，且不存在指向不存在事件的修正引用

#### Scenario: 丢失日志的完整副本被拒绝

- **WHEN** 用仅复制主文件、丢失未合并日志的副本恢复
- **THEN** 报告恢复失败，且原因属于恢复校验自身的失败类别（完整性检查失败、外键检查失败、期望值缺失、计数与期望值不符，或真实读取失败），而不是返回一个空但"完整"的存储

#### Scenario: 损坏备份被拒绝

- **WHEN** 用被截断或损坏的备份文件恢复
- **THEN** 报告恢复失败，错误来自恢复校验本身而不是调用方后续读取时才暴露

### Requirement: 不阻塞调用方事件循环

同步数据库操作 MUST 在调用方事件循环之外执行，使写入与查询期间事件循环仍能调度其他任务。写操作 MUST 串行执行；读操作 MUST NOT 因写事务而失败或长期等待，并 MUST 返回已提交的数据。任何网络请求或等待不得发生在数据库事务内。

#### Scenario: 写入期间另一任务获得调度

- **WHEN** 在事件循环中发起一次阻塞型写入，同时有一个独立任务等待调度
- **THEN** 该任务在写入返回之前执行完成，而不是等写入结束后才运行

#### Scenario: 写入进行中读取不被阻塞

- **WHEN** 一个连接正处于写事务中，同时发起读查询
- **THEN** 读查询成功返回已提交数据，既不含未提交变更也不因写事务而失败

#### Scenario: 并发写入串行且不丢失

- **WHEN** 多个不同事件并发写入
- **THEN** 全部写入最终可见，每条均可按 ID 取回，没有因竞争而丢失的事件

### Requirement: 存储不写健康内容到日志

存储层 MUST NOT 把事件数值、原始属性或完整载荷写入日志。失败路径 MUST 产生可定位的诊断日志，其中只包含事件 ID、指标名与错误类别。

#### Scenario: 失败路径有诊断且不含健康值

- **WHEN** 触发一次成功写入与一次失败写入
- **THEN** 失败写入产生日志且包含事件 ID 与错误类别，同时日志中找不到事件数值、原始属性内容或完整载荷
